## 0. 先读这一页

**不要重建应用底座。不要先做完所有领域设计。先完成一轮工程定型，再按真实业务闭环推进。**

整体顺序：

```text
盘点现有工程，确定第一轮范围
                ↓
领域划分与架构设计
                ↓
冻结增量技术决策、目录和开发规范

纵向实现、自动化测试、真实平台验证
```

第一轮交付目标：

> Relay 能通过一个接入实现，在一个 Meta 渠道上完成真实的文字消息收发，保存自己的记录，查询操作结果，并能够定位和解释失败。

随后使用**同一渠道的第二种接入实现**，检验公共契约和 Zernio 替换边界。不要等所有平台、所有消息类型、所有未来接口设计完才开始实现。

## 1. 项目上下文与范围

### 1.1 产品关系

```text
Vesact
├── Relay
│   面向开发者及需要独立使用渠道接入能力的用户
│   提供账号连接、统一 API、执行结果与事件通知
│
└── Studio
    面向普通用户的聚合应用
    使用 Relay 的渠道能力
    最终业务定位继续验证
```

Relay 可以有自己的控制台，用于连接账号、管理密钥、查看用量和诊断操作。它不等于纯后端项目，但也不应该因此长成另一个 Studio。

“单买账号”的具体商品和计费含义尚未在本轮确定；不要自行将它扩展为社媒账号代注册、交易或其他业务。

### 1.2 这次所说的“基建”是什么

不是部署、数据库、登录页面或整套 SaaS 模板，而是 Relay 的公共业务基础：

| 公共支撑域        | 要解决的问题                                                    |
| ----------------- | --------------------------------------------------------------- |
| **Connections**   | 账号归属、渠道授权、连接状态、外部 ID、可用能力、接入实现选择。 |
| **Execution**     | 幂等、持久化任务、执行尝试、限流协调、重试和结果核实。          |
| **Events & Sync** | 入站事件处理、业务数据同步、自己的事件、客户 Webhook 投递。     |

这些支撑 Messaging，并在后续被 Publishing、Analytics、Ads 复用。复用来自真实业务，不是先设计一个可以连接任意 SaaS 的通用平台。

### 1.3 当前明确不做

不重新选择 SaaS 模板，不迁移 Neon 到 D1，不重做现有认证和组织系统；不先实现完整 CRM、销售流程、AI 员工系统；不先做全部平台、全部权限、全部消息类型；不先建设微服务、插件市场、通用 Saga、事件溯源、动态 schema 引擎或自动供应商故障切换。

这些能力不是永久禁止，而是必须由明确需求和当前瓶颈驱动，不能作为“架构完整”的前置条件。

### 1.4 申请阶段：先用 Zernio 的开源客户端

申请各平台权限要一个用到全部权限的完整应用。Zernio 的 API 闭源，建在它之上的客户端开源（MIT），拼起来就是这个应用；它们只在申请阶段使用，之后换成 Relay 自己的实现。

| 仓库                                                         | 覆盖                                                                                    | 栈                                           | 指向自有 API           |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------- | -------------------------------------------- | ---------------------- |
| [unified-inbox](https://github.com/zernio-dev/unified-inbox) | 私信：WhatsApp、IG、Messenger、Telegram、X、Reddit、Bluesky，模板、按钮、语音、引用回复 | Next.js 15、shadcn、TanStack Query，无数据库 | `ZERNIO_API_URL`       |
| [ads-dashboard](https://github.com/zernio-dev/ads-dashboard) | 广告数据：Meta、Google、TikTok 等 7 家，campaign 下钻                                   | Next.js，无数据库                            | `ZERNIO_API_BASE`      |
| [latewiz](https://github.com/zernio-dev/latewiz)             | 发布排期：13 个平台                                                                     | Next.js 16、shadcn，经 zernio-node SDK       | SDK 的 `baseURL`       |
| [zernflow](https://github.com/zernio-dev/zernflow)           | comment to DM、关键词触发、流程、群发                                                   | Next.js 16 + Supabase + React Flow           | 设置页填 key，需改代码 |

没有开源的 analytics 界面。[openapi-specs](https://github.com/zernio-dev/openapi-specs) 是 13 个平台自己的 API 规范（Facebook、Instagram、TikTok…），写原生实现时用。

这四个客户端只认 Zernio 的接口形状，所以申请阶段 Relay 对它们暴露的接口要和 Zernio 一致；审核录屏跑的是自己的 App ID，这条路径后面接的是 Meta 原生实现，不是 Zernio 托管。

## 2. 核心原则：后续决策的判断依据

### 2.1 公共业务身份稳定，外部连接可以更换

Relay 使用自己的账号、会话、消息、发布和事件 ID。Zernio 或平台原生 ID 作为带作用域的外部引用保存。

更换接入实现，主要影响连接、映射和执行路径，不应迫使 API 客户更换整套业务接口。能够保持哪些历史关联，要以实际平台身份映射能力为准，不承诺无法验证的无感迁移。

### 2.2 统一高频语义，明确保留差异

公共内容与平台专属能力分开。不为了统一而削成最低能力公约数，也不把所有请求退化成任意 JSON。

不支持的关键能力应明确拒绝，或由调用者明确选择降级策略；不能悄悄丢弃字段后返回成功。

### 2.3 接受请求、下游接受、最终送达是不同事实

接口返回成功必须有明确含义。平台请求超时可能意味着结果未知，不等于确定未执行。业务操作与执行尝试分开，消息与投递回执分开，业务事件与 Webhook 投递分开。

### 2.4 自己保存必要业务记录，不做平台全量镜像

Relay 保存自己承诺提供的数据、执行状态与关联；不依赖查询时全部透传供应商。与此同时，不为未来可能的需求复制全部原始数据，也不承诺上游没有提供的历史或状态。

### 2.5 边界提前定，抽象从第二个真实实现中提炼

提前确定领域责任、归属、安全和公共契约约定。具体参数、限流方式和平台细节按业务逐步增加。

首个接入实现暴露问题，第二个实现检验共性。不要先为十几个未接入平台写空接口。

## 3. 工程推进顺序

### 3.1 一次整体定型，多轮小闭环交付

| 步骤              | 主要工作                                               | 最小产物                       | 完成标准                                         |
| ----------------- | ------------------------------------------------------ | ------------------------------ | ------------------------------------------------ |
| **1. 现状盘点**   | 读实际仓库，确认可复用能力与缺口。                     | 文件路径有依据的现状清单。     | 能说明保留、增加、不做什么；不是另一份选型报告。 |
| **2. 架构设计**   | 划领域、责任、依赖和数据归属，画发送与接收流程。       | 领域图、两条主流程、关键决策。 | 能解释第一条消息如何走完整个系统。               |
| **3. 工程定型**   | 确认增量技术、目录映射、契约和开发规范。               | 简明工程约定。                 | 可以在现有仓库落地，不需要整体迁移。             |
| **4. 契约与方案** | 设计当前业务链的输入、输出、状态、错误、事件及持久化。 | 一份可评审的功能切片方案。     | 不再需要边实现边猜公开语义。                     |
| **5. 纵向实现**   | 接口、权限、数据库、执行、接入、测试一起完成。         | 一个可使用的能力。             | 自动化测试与真实平台验证都有结果。               |
| **6. 设计回看**   | 修正被真实需求证伪的假设，记录差异。                   | 更新契约和必要决策。           | 下一条业务链能复用已有能力，而非重复造轮子。     |

前三步做一次主干定型，不反复重选底座；后面按切片循环。设计允许修正，但要指出新证据和影响，不能仅因为出现新工具就换方向。

### 3.2 不按技术层堆进度

避免：

```text
先建完全部数据库表 → 写完全部 Adapter → 写完全部 API → 最后整体联调
```

采用：

```text
一条业务契约
   → 权限与归属检查
   → 数据和执行状态
   → 平台调用或事件处理
   → 结果查询 / 客户通知
   → 故障测试与真实验证
```

每个里程碑都交付可演示、可验证的行为，而不是“目录已建好”“接口定义了几十个”。

## 4. 第一项任务：仓库盘点

### 4.1 必须从代码确认的事实

| 检查项        | 要确认什么                                                   |
| ------------- | ------------------------------------------------------------ |
| 两个应用      | 实际路径、启动入口、部署入口、构建与运行时边界。             |
| 共享 packages | 哪些已有明确职责，哪些目前被多个应用直接访问。               |
| API 层        | 当前路由、schema、服务实现、OpenAPI、客户端生成方式及版本。  |
| 认证与权限    | 用户、组织、成员、角色、API Key 和业务资源归属的已有设计。   |
| 数据库        | ORM、Neon 访问方式、事务能力、迁移流程、测试隔离方式。       |
| 异步执行      | 已有队列、Cron、任务记录、回调处理及补偿机制。               |
| 文件与媒体    | 现有存储、上传流程、访问控制、签名 URL、清理机制。           |
| 测试与发布    | 类型检查、单测、集成测试、真实运行环境测试和 CI 的实际命令。 |
| 平台集成      | 已有 Meta/Zernio 代码、凭据配置项、已实现能力和测试记录。    |

输出应引用真实文件路径，不要仅复述本文件。不能读取或输出生产 token、API Secret、完整客户消息等敏感内容。

### 4.2 盘点后的技术决策方式

每个调整只说明四件事：现状、实际问题、最小改动、验收方法。

缺少能力不等于必须新增产品。先检查现有依赖能否完成，再判断是否增加库或托管能力。不在这一步大规模重命名目录、重写业务或升级主要依赖。

## 5. 技术架构与目录规范

### 5.1 默认架构：契约驱动的模块化单体

```text
Studio / 外部开发者
        │
        ▼
Relay 公共契约：REST API + Webhook
        │
        ▼
领域用例：Connections / Messaging / 后续业务
        │
        ├── 归属与能力检查
        ├── 持久化、执行尝试与幂等
        └── 事件、同步与通知
        │
        ▼
领域接入契约
        │
        ├── Zernio 实现
        ├── Meta 原生实现
        └── 后续 TikTok / Google 实现
```

这是代码组织方式，不要求拆成独立服务。HTTP、Queue consumer、Cron 等入口可以调用同一组用例；部署单元是否分开，服从现有结构和真实运行需要。

### 5.2 层的职责

| 部分               | 负责                                                    | 不负责                            |
| ------------------ | ------------------------------------------------------- | --------------------------------- |
| **入口层**         | 解析请求、认证、建立调用上下文、返回响应或接收事件。    | 平台专属调用流程和整套重试规则。  |
| **领域用例**       | 业务状态、资源归属、有效能力、操作规则、事务。          | Zernio 或 Meta 的原始字段格式。   |
| **执行与事件支撑** | 持久化工作、尝试记录、补偿、投递与诊断。                | 所有领域共用的万能状态机。        |
| **接入实现**       | 授权协议差异、请求转换、原生 API 调用、错误和事件转换。 | 套餐、组织成员、Studio 销售流程。 |

执行模块应依赖一个受控的派发接口或显式注册表，不要让各领域和执行器互相导入形成循环依赖。普通函数组合即可，不为此建立插件平台。

### 5.3 目录示意：先模块化，再决定是否拆 package

以下是职责映射示例，不是要求覆盖现有目录：

```text
apps/
  relay/                      # HTTP、OAuth、Webhook、任务入口、控制台
  studio/                     # 消费 Relay 能力的应用

packages/
  relay-contracts/            # 公共输入、输出、错误、事件 schema
  relay-core/                 # 服务端实现
    connections/
    messaging/
    execution/
    events/
    integrations/
      zernio/
      meta/
  relay-client/               # 需要时生成或复用现有客户端

  ...已有 database、auth、ui、config 等 packages
```

初期 `relay-core` 可以是现有服务端 package 中的模块。`relay-client` 也可以复用现有生成客户端。只有明确的消费边界才拆包，不建立未来才会用到的空包。

### 5.4 依赖规则

公共契约不能导入数据库、密钥、CF 服务端 bindings 或平台 SDK。Studio 可以使用契约和客户端，但不能直接读写 Relay 业务表、调用平台 Adapter。

服务端领域依赖自己定义的接入能力，具体实现由运行入口组装。平台特有代码留在对应集成目录中，不散落到公共路由和 Studio 页面。

内部调用不必强制跨 HTTP，但必须进入同一应用服务边界，经过相同的归属、能力、状态和执行规则。不要把共享 package 当作绕过 Relay 的后门。

### 5.5 测试、命名和变更约定

沿用仓库已有命名风格。测试按当前项目惯例放置，确保每个 Connector 有可找到的脱敏 fixtures 和行为测试。原生字段命名限制在映射边界内。

一项功能的契约、实现、迁移和测试一起交付。不要维护两套人工同步的 OpenAPI；不要为了减少类型数量，让输入、输出和数据库行共用一个巨大 schema。

## 6. 技术栈决策：继承现状，只补缺口

| 能力                | 本轮决策                                                                            |
| ------------------- | ----------------------------------------------------------------------------------- |
| **基础工程**        | 保留 Supastarter 改造版、Cloudflare 部署和 Neon，不换模板、不换数据库。             |
| **API 框架**        | 以仓库为准。仍使用 Hono/oRPC 就沿用；已改成其他实现，不为本文件迁回去。             |
| **契约与校验**      | 复用当前 schema 工具，明确导出 Relay 公共契约，生成 OpenAPI。                       |
| **数据库与迁移**    | 复用当前 ORM、Neon 连接方式和迁移流程；需要事务的路径必须实际验证驱动能力。         |
| **认证、组织、Key** | 复用现有机制，补业务归属校验，不另外部署认证平台。                                  |
| **任务执行**        | 优先复用已存在方案；缺失时，CF Queues + Neon 持久化任务 + Cron 补偿是默认增量方案。 |
| **媒体**            | 复用当前存储；需要新建对象存储能力时优先评估 R2，不能假定已配置。                   |
| **长流程**          | 到多步骤发布确实需要时再加入 Workflows，不给每条聊天消息套一个 Workflow。           |
| **协调与实时**      | 不默认为每个账号建 DO。遇到明确跨实例协调或实时连接问题时再设计。                   |
| **测试与 SDK**      | 复用当前测试链，补真实 CF 环境验证、契约检查；对外需要时再生成客户端。              |
| **Effect**          | 暂不上全栈 Effect，也不自己仿造一套；将来只在具体执行模块验证收益。                 |

新依赖要回答：它解决了当前哪个问题，现有工具为什么不够，带来了什么维护成本。不得把“库支持”当成“仓库已经集成”。

运行时限制、库版本和官方配置都以当期文档和 lockfile 为准。本文不要求升级到最新大版本。

## 7. 三个公共支撑域怎么做

### 7.1 Connections：授权、资产与能力

先把概念分开，再决定是否需要独立表：

| 概念           | 含义                                                                |
| -------------- | ------------------------------------------------------------------- |
| **客户组织**   | 使用 Relay 的开发者或团队，优先映射到已有组织模型。                 |
| **代管客户**   | 开发者自己的终端企业；需要时增加轻量归属，不新建另一套认证体系。    |
| **Account**    | 可操作的渠道资产，例如 Facebook Page、IG 账号或 WhatsApp 业务号码。 |
| **Connection** | 授权关系、凭据、授予的权限、健康状态。一次授权可能关联多个资产。    |
| **Binding**    | Account 使用的接入实现、Connection 与外部资产引用之间的绑定。       |

直接使用 Relay 的客户可以映射到默认代管分组，不必把多层概念都强加给前端用户。归属上下文必须由服务端验证，不能信任请求里随意传入的组织或客户 ID。

能力检查分为：平台是否支持、当前接入实现是否实现、App 是否获准、用户实际授予什么、资产权限是否足够、当前操作条件是否允许。

先用代码能力定义和运行时检查解决，不建设动态 schema 系统。静态“支持发消息”不等于当前会话可以发送任意内容。

参考 Apideck Vault 的连接生命周期：创建、更新、可调用、暂停、删除、撤销是不同概念；这是边界参考，不是全量功能清单。[R8]

### 7.2 Execution：持久化意图与可解释的尝试

建议的最小出站流程：

```text
校验调用者、账号归属、参数、能力、幂等键
                  ↓
数据库事务：业务记录 + 待执行记录
                  ↓
投递 taskId，消费者领取并固定本次接入绑定
                  ↓
调用下游，记录尝试与外部引用
                  ↓
更新结果；必要时等待回执或进行核实
```

数据库是“Relay 已接收哪些工作、它们现在是什么状态”的事实来源；队列只是传递执行机会。不要在持久化前返回“已接受”，也不要把入队成功等同于业务成功。

待执行记录可以同时承担 outbox 的角色。是否拆表取决于实现需要，不为模式名称多造表。数据库提交后入队失败，由 dispatcher/Cron 补投；已经派发但长期未完成的任务也必须可诊断。

Cloudflare Queues 采用至少一次投递，且不保证顺序。因此消费者需要去重和领取控制；同一会话需要的发送顺序由应用明确保证。[R1][R2]

**任务租约到期不是安全重发的证据。**进程可能在下游成功、数据库尚未更新时中断。是否重试应依据操作性质和平台证据；无法确认时保留结果未知，不能把它自动归为可重试失败。

Stripe 的错误文档将某些服务端错误明确视为不确定结果；借鉴的是这个语义，不是把 Stripe 的幂等保证套到所有下游平台上。[R3]

此外，刷新凭据的竞争可能发生在同一个 Connection 下，不一定是一账号一把锁。API 入口限流、客户套餐额度、平台 App/账号/收件人限流分别处理，不用一个计数器混合表示。

### 7.3 Events & Sync：两种事件链分清

入站：

```text
验签与基本校验
    → 可靠接收
    → 映射账号与连接
    → 去重、规范化
    → 更新领域数据并可靠记录待发送事件
```

出站：

```text
Relay 事件
    → 找到有权接收的客户端点
    → 签名并投递
    → 保存投递尝试
    → 重试或人工恢复
```

不可靠接收就不要假装成功。单个上游请求包含多条事件时，要明确拆分和去重单位。重复消息回显、重复 webhook 和同一消息不同状态事件是不同情况。

不要仅以 `messageId` 去重所有事件，否则可能丢掉编辑、送达、已读等变化；使用上游事件身份及适用的事件类型、版本等建立规则。

同步第一版只做当前通道的初次读取、后续事件、必要补查、可见的覆盖范围和同步进度。Zernio 当前明确：Facebook/Instagram 连接时补入的历史私信不会触发 `message.received`，因此只接 Webhook 不足以获得历史。[R6]

客户事件与投递尝试分开，重复投递保持稳定 event ID。事件入库与对应业务变更之间也要有可靠衔接，不能更新数据后因进程中断永久丢通知。参考 Svix 的投递、重试和恢复机制。[R11]

## 8. 业务领域：当前深入 Messaging，后面只定边界

| 领域           | 核心对象与问题                                          | 第一轮范围                       |
| -------------- | ------------------------------------------------------- | -------------------------------- |
| **Messaging**  | 会话、参与者、渠道身份、消息、附件、发送结果、回执。    | 实际设计并实现文字收发闭环。     |
| **Publishing** | 发布意图、平台目标、媒体、计划时间、各目标结果。        | 仅保留边界；聊天核心稳定后实施。 |
| **Analytics**  | 指标、维度、统计周期、数据新鲜度、来源和口径。          | 不提前建万能指标模型。           |
| **Ads**        | 广告账号、Campaign 与平台各级投放对象、审核和投放状态。 | 不把广告塞进 Post，不提前实现。  |

### 8.1 Messaging 第一轮必须决定的语义

**会话保持渠道内语义。**同一买家在 WhatsApp 和 IG 上联系，不自动合成一个 Relay 会话。跨渠道 CRM 客户合并留给 Studio。

**参与者与渠道地址分开。**内部客户身份、平台用户标识和联系地址不是同一概念。外部标识要保留平台/App/连接作用域，不能假定跨 App 通用。Twilio Conversations Classic 的参与者与 messaging binding 可作为建模参考，而不是全量复制对象。[R9]

**提交与投递分开。**本地已排队、下游接受、接收者送达、已读分别建模。不能把缺少回执表示为 `false` 或伪造成功，也不能让迟到事件机械覆盖更可靠的已知状态。

**渠道状态与业务工作流分开。**平台的已读回执属于 Relay 能力；销售负责人、内部备注、客户阶段，以及某个 Studio 员工是否查看过，属于上层应用。

**回复与主动发起分开考虑。**首轮可只做已有会话回复；契约不能永远假设必须先有会话。未来平台允许的首触达/模板消息单独设计并检查条件，不能默认任意平台可主动发信。

### 8.2 后续展开顺序

聊天先一个 Meta 通道，随后按实际需求补附件、回执和其他 Meta 通道；发布先立即发布，再多目标、定时和视频处理；分析先已有账号/内容的数据读取，再历史趋势；广告先只读，再有限可控写入，最后创建复杂投放。

平台优先级不等于每个平台必须实现四个领域。Google 本阶段默认考虑 YouTube 与后续 Google Ads，不自动加入 Gmail/Google Chat。TikTok 聊天要单独核实准入与实现来源；不能因为 Zernio 提供 TikTok 接入，就推定它能够代理 TikTok Inbox。[R7]

## 9. API 契约设计：先把公开承诺写清楚

### 9.1 契约先于大规模实现，但与数据模型一起推敲

每条业务链先确定输入、输出、状态、错误、事件及实例，再补保存和执行方案。不要先建所有表再自动暴露，也不要只画接口而忽略执行可行性。

公共契约应独立于 Studio 的页面结构和 Zernio 的响应格式。OpenAPI 来自仓库中的契约事实来源；手写示例用于解释语义，不成为另一份需要人工同步的完整规范。

### 9.2 第一批资源候选

下表是资源边界示例，具体路径和命名需结合现有框架确认，不要求现在全部实现：

| 资源                       | 目的                                       |
| -------------------------- | ------------------------------------------ |
| Connect sessions           | 创建短期有效的渠道连接流程。               |
| Accounts / Connections     | 查看资产、健康状态、能力、重新授权与断开。 |
| Conversations / Messages   | 会话、历史、发送、结果查询。               |
| Media                      | 上传、归属与附件引用，到附件切片时实现。   |
| Webhook endpoints / Events | 配置通知、检查投递、重投。                 |
| Posts                      | 到发布阶段再增加。                         |

OAuth callback 和上游 Webhook 是专用入口，不与普通 API Key 请求混淆。不要默认把控制台管理接口全部导出为公共 API。

### 9.3 契约共同约定

| 事项               | 需要定下来的内容                                                                      |
| ------------------ | ------------------------------------------------------------------------------------- |
| **认证与归属**     | API Key 属于谁、可访问哪些资源；Studio 服务端如何调用；浏览器不得持有总权限服务密钥。 |
| **公共 ID**        | 由 Relay 生成，不暴露供应商 ID 作为唯一业务身份。                                     |
| **请求与响应**     | 输入、输出、PATCH 语义分清；数据库内部字段和凭据不进入公共响应。                      |
| **异步写入**       | 2xx/202 的含义、查询入口、最终结果事件、结果未知的表达。                              |
| **幂等**           | Key 作用域、有效期、请求摘要、处理中/已完成行为、相同 key 不同内容的错误。            |
| **分页**           | 排序、opaque cursor、边界变化行为；不要把供应商 cursor 原样变成永久公共承诺。         |
| **错误**           | 稳定机器码、可理解说明、request ID、安全的诊断信息；不只返回原始平台错误。            |
| **时间与数据覆盖** | 统一时间表示，区分发生时间、接收时间、更新时间；说明缓存与历史覆盖。                  |
| **扩展**           | 通用字段和平台专属参数分开，平台与参数类型关联；未知/不支持不能静默成功。             |
| **版本与兼容性**   | 公共契约变更检查；新增枚举等也要评估客户端影响；已使用契约不得随意修改。              |
| **Webhook**        | 稳定事件 ID、签名、版本、重投语义、可能的重复/乱序，以及查询补偿方式。                |

尚未确定的细节，例如幂等 TTL、分页默认大小、具体状态码，应在对应切片实现前确定并写入规范，不能散落成互相矛盾的默认值。

### 9.4 文字发送示例

以下只展示建议语义，不是已实现接口：

```http
POST /v1/conversations/conv_123/messages
Authorization: Bearer <relay_api_key>
Idempotency-Key: followup-001
Content-Type: application/json

{
  "content": {
    "type": "text",
    "text": "您好，想确认一下采购数量。"
  }
}
```

建议返回：

```http
HTTP/1.1 202 Accepted
Content-Type: application/json

{
  "id": "msg_123",
  "conversationId": "conv_123",
  "status": "queued"
}
```

这里的承诺是“Relay 已持久化接收请求”，不是“消息已送达”。状态字段是否拆成提交状态与投递状态，在正式 schema 中决定；不能用一个模糊状态掩盖两者区别。

同一个幂等 key 与相同请求应关联同一业务操作，不因重试新增消息。客户端 key 在 Relay 生效，不代表下游天然具备同样的幂等保证。

平台独有能力使用明确、可验证的扩展结构。Merge 的 Supplemental Data 值得学习“原始数据、额外字段、原生操作”的边界，但本轮不实现任意带凭据 HTTP 代理。[R10]

## 10. Zernio 接入与原生替换

### 10.1 接入契约按领域拆，不建万能 Adapter

使用小范围、明确职责的 Messaging 接入契约；后面需要时增加 Publishing、Analytics、Ads。一个 Zernio 模块可以实现多个领域契约，不必为每个平台创建一个重复包装层。

Zernio 实现负责授权连接转换、请求转换、结果与错误转换、事件转换、外部 ID 映射。它不直接决定 Relay 的客户模型、公共状态、计费或所有数据表。

Zernio 的 Profile/Account 多租户关系仅作为内部映射，不能要求 Relay 客户先理解和创建 Zernio Profile。[R5]

### 10.2 选路规则

第一版一账号一条 active messaging binding；确有需要时再按 Messaging/Publishing 两个能力组分别指定。不要实现按错误自动换供应商。

待执行但尚未提交下游的任务，可以按照明确规则选择绑定；一旦首次提交到下游，应固定该操作的绑定及外部引用，后续查询、核实和回执继续沿用它。

Zernio 只是过渡实现，也可以成为长期可选实现；不为了“必须最终删掉依赖”而妨碍真实交付，但需要持续掌握用量、费用、能力和替换成本。

### 10.3 迁移的真实边界

代码可替换，不代表授权和历史可以自动迁移。实施前需要确认新 App 授权、渠道资产身份、事件接收关系、跨 App ID 范围，以及未完成任务的处理方式。

只有有可靠依据时才把新连接关联到已有 Account/Conversation。不能仅凭用户名、显示名或相似内容自动合并。无法可靠关联时，保留旧历史与明确的迁移限制，必要时创建新渠道会话，不伪造连续性。

旧绑定不能在仍有任务或回执依赖时立即删除；同时应有最终清理与凭据撤销策略，不能无限期保留敏感授权。

### 10.4 对模糊失败的特殊要求

Zernio 当前文档说明发送接口仅保存成功响应的幂等重放结果，模糊超时/服务端错误可能发生在平台已接受消息之后，且查询列表为空也不足以证明未发送。[R4]

因此 Adapter 必须表达“结果未知/需要核实”，不能把所有非 2xx 自动交给无限重试。后续更新供应商版本或行为时，重新验证这类关键语义。

### 10.5 第二实现的验收重点

共同能力使用同一组契约测试；独有能力明确标注。验证公共 API、资源归属、ID 映射、错误分类、历史可见性和未完成任务处理。

不能用“换了一个环境变量还能启动”当作替换成功。也不要求为了达到同等能力而抹掉原生实现的额外功能。

## 11. 第一轮里程碑：A → B → C → D → E

### A：工程定型

**目标：** 形成能指导第一条真实链路的设计，而不是完整平台蓝图。

| 项目     | 要求                                                                                 |
| -------- | ------------------------------------------------------------------------------------ |
| 输入     | 实际仓库、本文件、现有部署与数据库配置结构。                                         |
| 工作     | 盘点工程；领域与依赖设计；映射目录；确定首个通道与接入路径；设计第一条文字发送契约。 |
| 产物     | 架构说明、仓库约定、Core + Messaging v0.1、实现切片和验收用例。                      |
| 出口条件 | 第一条链路的责任、接口、数据和失败处理不再有阻塞性歧义。                             |
| 不做     | 批量创建空包、大规模重构、生产迁移、全部平台或全部未来接口。                         |

这里的构建/测试验证是确认现状可运行，并检查设计所需的最小接线，不为了“完成架构”先实现全部支撑域。

### B：第一条出站链路

**目标：** 用合法可用的测试账号，向已有会话发送一条文字消息，持久化并查询结果。

实现一个写入契约，贯通认证与资源归属、消息记录、幂等、任务、一个接入实现、结果查询和诊断。

可以暂时用受控的测试配置导入账号与会话，但不能在业务代码里硬编码全局生产 token、绕过客户隔离，或把临时导入方式包装成正式连接流程。

**验收：** 平台侧真实收到消息；重复请求不会创建新的 Relay 操作；明确失败可解释；下游结果不确定时不盲目重发；两个测试客户不能相互访问。

### C：第一条入站链路

**目标：** 真实来消息能进入 Relay，查询会话和历史，并能接着回复。

实现签名验证、可靠接收、账号映射、事件去重、消息与参与者记录、查询接口，以及必要的回显关联。

**验收：** 重复 webhook 不生成重复业务记录；同一消息不同事件不会被误去重；可从一次原始事件追踪到 Relay 消息；查询不造成跨租户泄露。

B、C 的顺序可按平台限制微调。例如必须先收到消息才能形成合法会话时，允许先实现必要的入站接收。不能为了严格按表格顺序构造不真实的测试条件。

### D：最小可交付聊天能力

**目标：** 一个真实使用者能够持续使用，不依赖开发者手工改数据库。

补齐正式连接/重新授权/断开、必要历史读取与覆盖说明、客户事件通知、简单诊断界面、任务恢复和数据清理路径。Studio 或 Relay 的最小测试界面都可用于验收，不要求完成 Studio 产品。

**验收：** 从连接到日常收发可走完整流程；授权过期可识别；失败任务可定位；Webhook 失败可重投；历史不完整时有说明；基础业务不会因一次短暂中断永久丢失。

付费前再明确套餐与支付联动。现阶段可以管理员授予额度，但权限判断要有统一入口，不能散落到平台实现里。

### E：同一渠道验证第二种接入实现

**目标：** 用同一套公共 Messaging 契约验证 Zernio 与原生实现的边界。

在真实可用的权限和测试资产下实现第二条路径，共用测试，核实连接迁移、外部 ID、历史、未完成操作和事件接收策略。

**验收：** 调用者无须选择供应商；共同能力语义一致；差异能被能力模型解释；可验证的资源身份保持稳定；无法迁移的内容明确记录；旧操作不会因切换而重复执行。

原生权限申请可以与 B—D 并行。若权限仍在等待，允许继续完善当前通道或扩展已有可用能力，但要将“真实原生验证未完成”标成阻塞，不能拿 mock 结果冒充 E 已通过。

### 阶段切换标准

A 之后停止扩写总蓝图；D 之后评估是否已形成最小交付能力；E 用于检验抽象，不是继续加入无限基础设施的理由。

首个聊天核心稳定后，按实际需求补附件、回执和其他 Meta 通道，再进入 Publishing。不要以“聊天还存在边缘功能”为由无限延后发布领域。

## 12. 并行轨道：原生权限与测试资产

维护一张轻量台账即可，不建立复杂项目系统：

| 平台/API 产品   | 所需能力 | 当前实际权限              | 测试资产 | 已实现演示 | 申请状态 | 下一步         |
| --------------- | -------- | ------------------------- | -------- | ---------- | -------- | -------------- |
| Meta 的具体产品 | 待确认   | 待读取控制台/实际配置核实 | 待确认   | 待完成     | 待确认   | 选首条真实链路 |

不要只写“Meta 已通过”。App 产品、scope、访问级别、资产权限和测试条件要能区分。

审核演示必须使用自己的 App 和实际获准的测试路径。复用开源 UI 或 Zernio 生产接入不等于已经完成自己的原生权限证明。每次申请使用当期官方要求，不沿用历史截图和未验证的权限清单。

真实测试发送只使用有权限的测试账号、收件人和资产；涉及客户生产消息、账号切换或付费动作，先明确授权范围，不能把自动化测试直接指向生产客户。

## 13. 测试、安全与可运营性的完成定义

### 13.1 每条切片的 Definition of Done

- [ ] 契约、示例、状态和错误含义已明确，OpenAPI 与实现没有人工分叉。
- [ ] 所有资源引用都检查所属客户，敏感凭据与原始错误不泄露。
- [ ] 需要的迁移已通过项目既有流程，未擅自操作生产数据。
- [ ] 正常路径、明确失败、重复请求/事件和结果不确定路径有测试。
- [ ] 有运行环境测试结果；真实平台验证已完成，或明确列为阻塞而非默认为通过。
- [ ] 能通过 request/message/task/event 等关联 ID 定位执行过程。
- [ ] 本轮变更没有让 Studio 直接依赖平台实现或 Relay 数据库内部结构。
- [ ] 文档、测试与实现同批更新，剩余限制已经写明。

### 13.2 跨切片最低验证矩阵

| 场景                               | 期望行为                                   |
| ---------------------------------- | ------------------------------------------ |
| 客户 A 使用客户 B 的资源 ID        | 拒绝访问，不泄露资源详情。                 |
| 同幂等 key、同内容重复提交         | 关联同一业务操作；不新增发送意图。         |
| 同幂等 key、不同内容               | 返回稳定、明确的冲突错误。                 |
| 数据库提交后入队失败               | 任务可补投，不永久消失。                   |
| 队列重复投递                       | 不因重复消费而自动重复执行副作用。         |
| 下游已执行但本地未落结果           | 核实或结果未知，不盲目再发。               |
| Webhook 重复、乱序、提前于发送响应 | 能关联、去重或暂存待关联，不丢掉有效状态。 |
| 凭据过期/撤销、账号断开            | 明确状态，不无限刷新或无限重试。           |
| 客户 Webhook 超时                  | 重投同一事件，保留尝试记录，不重做业务。   |
| 历史覆盖不完整                     | 返回可解释限制，缺失不冒充空白事实。       |

### 13.3 第一轮必备安全和诊断

接触真实 token 前确认加密保存和密钥分离；OAuth 校验 state、回调与适用的 PKCE；Webhook 验签并限制负载；文件和客户 Webhook URL 做访问控制与 SSRF 防护，不能开放内网地址、元数据地址或任意凭据代理。

日志默认记录关联 ID、操作类型、耗时与脱敏错误，不默认保存完整聊天正文、token 或长期原始 payload。凭据、消息、附件、事件和日志都要有保留与清理规则；删除路径应覆盖映射、缓存及恢复后的清理策略。

不先做漂亮监控大屏，但至少能查看连接健康、操作记录、失败/未知任务和 Webhook 投递。要实际验证恢复路径，不能只声明“供应商有备份”。

目标用户网络下的 API、控制台和附件访问要在早期实测；不要未经测试先设计第二套国内外基础设施。

## 15. 开发 Agent 的工作方式

### 15.1 决策分工

| 事项                                       | 处理方式                                   |
| ------------------------------------------ | ------------------------------------------ |
| 第一轮范围、产品责任、公开语义             | 提出明确建议，由项目负责人拍板。           |
| 已定边界内的函数组织、测试、常规实现       | Agent 自主推进，不为每个小改动反复确认。   |
| 新核心依赖、大版本升级、框架或数据库替换   | 单独说明理由、影响与替代方案，不静默执行。 |
| 破坏性公共契约、租户边界、重试语义变化     | 先评审，再实现。                           |
| 生产迁移、数据删除、真实客户发送和授权切换 | 获取明确授权，遵守现有发布流程。           |

并行 Agent 可以做独立调研、fixtures、测试和已经冻结契约的局部实现。第一轮领域模型、公共契约、数据库核心关系由同一个整合负责人维护，避免各自发明一套事实。

### 15.2 每个实现任务使用同一种格式

```text
目标：用户可以完成什么，而不是要新增哪些文件。
范围：本次包含和明确不包含的内容。
现有入口：已核实的目录、模块、依赖和命令。
契约：输入、输出、状态、错误、事件和关键示例。
方案：归属检查、持久化、执行、接入与失败处理。
验证：自动化测试、真实测试资产、验收证据。
变更风险：迁移、兼容性、生产影响和必要的回退方式。
```

每轮汇报只需要：完成了什么、如何验证、未完成/阻塞是什么、接下来做什么、需要负责人决定什么。不要用大量术语和新增目录掩盖尚未跑通的链路。

### 15.3 少量持续维护的文档

优先复用已有文档路径，建议保留四类内容，不要求强制新建四个文件：

| 文档                      | 内容                                               |
| ------------------------- | -------------------------------------------------- |
| **架构说明**              | 边界、依赖方向、身份归属、关键不变量和少量决策。   |
| **Core + Messaging v0.1** | 第一批公共契约、模型、状态、错误、事件及已知限制。 |
| **实施计划**              | 当前里程碑、下一切片、权限与测试阻塞。             |
| **开发约定 / AGENTS.md**  | 实际命令、目录规范、依赖限制、测试和汇报规则。     |

不要覆盖仓库现有 `AGENTS.md`；先阅读并合并必要约定。OpenAPI 本体由契约生成，不另外维护一份完整手写接口文档。

```text
- 业务优先级为 Messaging → Publishing → Analytics → Ads，平台优先 Meta → TikTok → Google。
- Zernio 必须能作为原生权限未完成时的接入实现，但不能决定公共模型。

本轮只完成里程碑 A：工程盘点与第一轮设计。

请完成：
1. 读取真实代码，列出可复用能力、关键文件路径与当前缺口。
2. 给出 Connections、Messaging、Execution、Events & Sync 的职责和依赖边界。
3. 将建议映射到现有目录，不大规模重构、不建立大量空 package。
4. 冻结必要的增量技术选择；沿用现有部署、Neon、框架和认证，不重新选底座。
5. 设计第一条“向已有会话发送文字消息”的公开契约与数据/执行方案。
6. 同时画出消息入站流程，避免出站设计与后续收消息冲突。
7. 给出 B—E 的小切片计划、验收用例，以及真实权限/测试资产的待确认清单。
8. 在现有文档体系中提交这些成果，汇报需要负责人拍板的少量问题。

约束：
- 不假定 Supastarter 官方默认依赖等于当前仓库。
- 不迁 D1、不更换模板、不重做已有认证、不引入全栈 Effect。
- 不把全部业务、全部平台或所有 API 设计完才进入实现。
- 不将数据库类型直接暴露为公共 schema。
- 不让 Studio 绕过 Relay 业务边界。
- 不实现失败自动切供应商；不把结果未知自动当成可重试失败。
- 不输出 secret；不修改生产数据；不擅自给真实客户发消息。
- 缺少真实权限或测试资产时，明确写成阻塞，不伪造测试通过。

本轮完成后先汇报设计和待确认项，不自动进入全量实现。
确认后，下一轮直接实现第一个纵向业务闭环，而不是继续扩写总架构。
```

## 最后的执行标准

**先完成足够指导第一条链路的设计，再用真实实现验证设计。**

第一轮的成功不是“架构看起来完整”，而是：

> 在现有 Vesact 工程里，Relay 的边界清楚、公开语义可解释、第一条聊天链路可靠可用，并且能够用第二种接入实现验证它不依附于 Zernio。

做到这里，就进入业务迭代。后续 Publishing、Analytics 和 Ads 复用已经被验证的基础，而不是继续为未来建设基础。
